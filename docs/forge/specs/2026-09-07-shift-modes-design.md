# Уровни пунктов, режимы смены и тревоги

Дизайн от 07.09.2026. Решения владельца — D050…D056 в `docs/forge/decisions.md`.
Этот документ объясняет, почему сделано именно так; что решено — в решениях.

## Задача

Менеджер выходит на смену, зная, что людей меньше стандарта. Полный чек-лист в такой
день заполняется как попало или никак. Продукт даёт градацию: у пункта есть уровень,
у смены — режим, и режим решает, какие уровни сегодня показывать.

## Уровни пункта

`Item.critical: boolean` заменён на `Item.severity: "critical" | "major" | "normal"`.

**Миграции данных нет и не будет.** Пункт живёт внутри JSONB — в
`checklist_versions.sections` и `submissions.snapshot`, то есть в замороженных
документах, переписывать которые запрещено (принцип 3, D002). Поэтому уровень не
мигрируется, а выводится при чтении:

```
severityOf(item) = item.severity ?? (item.critical ? "critical" : "normal")
```

`Item.critical` остаётся в типе как `@deprecated`: новый код его не пишет, но версии,
опубликованные до 07.09.2026, читаются правильно вечно. Уровня «важный» в старых данных
не возникает — решать задним числом за методиста, что у него было важным, мы не будем.

Комментарий при провале теперь требуют два верхних уровня, а не один
(`requiresCommentOnFailure`): «не выполнено» без единого слова о причине не даёт
управляющему ничего, кроме тревоги без предмета.

## Режим смены

Три режима с жёсткой матрицей (D056), зашитой в `data/severity.ts` и больше нигде:

| режим | критичные | важные | обычные |
|---|---|---|---|
| `normal` — обычная смена | ✓ | ✓ | ✓ |
| `reduced` — с ограничениями | ✓ | ✓ | |
| `critical` — критичная | ✓ | | |

Справочника режимов нет сознательно: перечисление в коде нечего переливать при
появлении пространств стран (D050, D051).

`sectionsForMode` убирает выпавшие пункты и **не оставляет пустых секций**. Если в
режиме не осталось ни одного пункта, чек-лист на станции не открывается вовсе —
состояние `no-checklist`, а не пустой экран с кнопкой «Отправить».

### Хранение

`store_shift_modes` (миграция `0006_shift_modes`) — таблица только пополняется:
перестановка режима это новая строка. Действующий режим — самая свежая строка по паре
(пиццерия, местная дата); строки нет — значит полная смена.

Местная дата считается базой из `stores.timezone` (D026), а не в JavaScript: сутки
смены кончаются там, где смена работает. Проверено тестом на `Asia/Almaty`: в 20:00 UTC
там уже следующие сутки, и утренний режим погашен.

Владельца по D051 колонкой заводить не понадобилось — он выводится через пиццерию.

`submissions.mode` хранит режим, в котором заполняли. Читается на сервере в момент
отправки, а не приходит из браузера: вечерняя перестановка режима не имеет права
переписать, в каком режиме заполняли утром.

Снимок (`submissions.snapshot`) сохраняется **полным**, а не усечённым по режиму:
иначе история стёрла бы сам факт сокращения — ровно то, что управляющий и должен видеть.

## Тревоги

Объекта «день» и действия «закрыть день» нет (D053). Тревога вычисляется запросом в
момент, когда на неё смотрят; ни таблицы, ни фоновой работы, ни планировщика.

Два источника:

1. **Провал критичного пункта** — событие в момент отправки.
2. **Пропущенный чек-лист** — состояние: версия опубликована и привязана к станции,
   окно за сегодня по местному времени закончилось, заполнения нет, и в действующем
   режиме в чек-листе оставался хотя бы один пункт. Последнее условие обязательно,
   иначе критичная смена порождала бы тревоги по чек-листам, которые сама же отменила.

Известная ложь, принятая осознанно (D054): в нерабочий день пропуск сработает зря —
отличить закрытую пиццерию от забытого чек-листа без календаря нечем.

## Состояние работ на 07.09.2026

### Сделано и проверено

727 модульных тестов зелёные, `tsc --noEmit` чист.

- `data/severity.ts` — уровни, матрица, `severityOf`, `sectionsForMode`,
  `requiresCommentOnFailure`, `isSeverity`, `isShiftMode` + 22 теста.
- `data/types.ts` — `Severity`, `ShiftMode`, `Item.severity`, `Item.critical` как
  устаревшее.
- `data/shift-modes.ts` — `getShiftMode`, `setShiftMode`, `listShiftModeChanges`
  + 8 тестов на настоящей базе, включая часовые пояса.
- Миграция `0006_shift_modes` (прямая и обратная) + запись в журнале Drizzle.
- `submissions.mode` проведён через `saveSubmission`, `SubmissionRow`, `SubmissionDetail`.
- `fill` — уровень вместо булева признака во всей цепочке; комментарий требуют оба
  верхних уровня; режим читается на сервере при отправке.
- `feed` — уровень в модели и карточке.
- `editor` — переключатель на три положения вместо тумблера критичности; разбор
  старого признака из черновиков; предпросмотр показывает метку уровня.
- Ключи локализации для обоих языков.

### Не сделано

1. **Экран выбора режима на станции.** Главное, чего не хватает: `loadFillTarget`
   пока не различает «режим на сегодня не выбран» и отдаёт чек-лист целиком, не
   фильтруя его по режиму. Нужны: состояние `needs-mode` в `FillTarget`, серверное
   действие выбора режима по коду станции (с ограничением частоты, как у отправки),
   компонент выбора и строка «Смена: … · сменить» в шапке.
2. **Фильтрация чек-листа по режиму на экране.** `sectionsForMode` написан и покрыт
   тестами, но в `FillScreen`/`buildFillView` ещё не вызывается.
3. **Показ режима в ленте.** `submissions.mode` пишется и читается, но на экране
   не показан; пункты, не запрошенные в этом режиме, в карточке никак не помечены.
4. **Тревоги.** Не начаты вовсе: ни запроса, ни экрана.
5. **Предпросмотр в режиме** для методиста (`PreviewScreen`).
6. **Демонстрационный сид** (`demo/dataset.ts`) не показывает ни трёх уровней, ни
   сокращённой смены.
7. **Сквозные проверки.** `e2e/editor.spec.ts` обращается к `item-critical` и
   `data-critical`, которых больше нет. Прогон Playwright после этой правки **не
   запускался** — это единственное место, где работа заведомо красная.
