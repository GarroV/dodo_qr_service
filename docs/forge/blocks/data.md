# Block: data

## Назначение

Схема данных, миграции и единственный слой доступа к базе. Все остальные блоки ходят в данные только через него — это и архитектурное решение, и правило, проверяемое границами модулей.

## API-контракт

```ts
// схема
countries, stores, stations, checklists, checklist_versions, blocks, submissions

// типы
type Item = { id: string; title: Record<string,string>; type: 'bool'|'number'|'text';
              critical: boolean; min?: number; max?: number; hint?: Record<string,string> }
type Section = { id: string; title: Record<string,string>;
                 source: 'own' | { blockId: string }; items: Item[] }
type Answer = { itemId: string; value: boolean|number|string; comment?: string; at: number }

// функции
getPublishedVersionForStation(stationCode: string, at: Date): Promise<VersionWithChecklist | null>
getDraft(checklistId: string): Promise<ChecklistVersion | null>
publishVersion(checklistId: string): Promise<ChecklistVersion>   // вставка строки, не update
saveSubmission(input: { versionId: string; answers: Answer[]; startedAt: number }): Promise<string>
listSubmissions(filter: { countryId?; storeId?; stationId?; from?; to? }): Promise<SubmissionRow[]>
getSubmission(id: string): Promise<SubmissionDetail | null>
```
Частичный уникальный индекс: одна опубликованная версия на чек-лист. Все отметки времени сервера — `now()` базы, не клиентские.

## Зависимости

`core`

## Definition of Done блока

1. Миграции применяются с нуля и откатываются.
2. `publishVersion` создаёт новую строку, прежняя версия побайтово не меняется — тест сравнивает содержимое до и после.
3. `getPublishedVersionForStation` возвращает версию по окну времени: утренний чек-лист в 09:00, вечерний в 21:00, `null` в 15:00, если ни одно окно не подходит.
4. Заполнение ссылается на конкретную версию; после публикации следующей версии старое заполнение читается без изменений.
5. Неизвестный код станции даёт `null`, а не исключение и не чужие данные.
6. Покрытие слоя доступа тестами с реальной базой в контейнере.

## Решения, принятые внутри блока

| Решение | Почему |
|---|---|
| У версии три состояния: `draft`, `published`, `archived` | Частичный уникальный индекс держит одну опубликованную версию на чек-лист. Публикация следующей версии переводит прежнюю в `archived` — меняется только признак, содержимое (секции, номер, время публикации) остаётся тем же байт в байт |
| У черновика нет номера версии и времени публикации, у опубликованной и архивной — есть | Ограничение `check` в базе: состояние и номер не разъезжаются даже при вставке мимо слоя доступа |
| Один черновик на чек-лист — тоже частичным уникальным индексом | `getDraft` по контракту возвращает одну строку; два черновика сделали бы ответ недетерминированным |
| Удаление страны, пиццерии, станции и версии запрещено, пока на них ссылается история (`on delete restrict`) | Принцип 3: история заполнений неприкосновенна. Исключение — `checklists.station_id`: удаление станции отвязывает чек-лист (`set null`), но не трогает ни его, ни заполнения |
| Заполнение хранит `station_id` рядом с `version_id` | Перенос чек-листа на другую станцию (T024) не должен задним числом переписывать, где заполняли |
| Станция замораживается в `checklist_versions` при публикации, и заполнение берёт её оттуда | `checklists.station_id` — обычная мутируемая колонка: читать её в момент сохранения значит записывать заполнение туда, куда чек-лист перевязали, пока сотрудник заполнял (T056). Клиент станцию по-прежнему не передаёт: она выводится сервером из версии |
| `getPublishedVersionForStation` отдаёт версию, только если её замороженная станция совпадает со сканируемой | Иначе заморозка ломает вторую половину сценария: после переноса чек-листа станция B получала бы версию, замороженную на A, и заполнение с B уходило бы в историю A. Следствие: после переноса чек-листа его надо опубликовать заново — на новой станции до этого ничего не отдаётся |
| Пустое окно (`window_start = window_end`) запрещено базой, а окно через полночь разрешено | Равные границы делают условие выбора версии всегда ложным: чек-лист не открывается никогда и молча. Конец раньше начала — наоборот, штатный вечерний чек-лист |
| У пиццерии есть часовой пояс, и окно чек-листа сравнивается с её местным временем | Этого требует контракт блока `catalog` (`createStore({ countryId, name, timezone })`), и без пояса утренний чек-лист в стране с большим сдвигом открывался бы среди дня. Момент времени переводится в пояс пиццерии прямо в запросе |
| Снимок для ленты и карточки читается из строки заполнения, а не из версии | Иначе вторая опора истории (D002) мнимая: снимок хранится, но не используется, и одной правки версии мимо слоя доступа хватает, чтобы переписать показанное сотруднику |
| Верхняя граница размера JSONB стоит в базе, а не только в блоке `fill` | `submissions` — единственная таблица, куда пишет неопознанный человек из интернета. Если единственная защита живёт в коде вызывающего, забытая проверка означает, что база примет что угодно |
| `listSubmissions` ограничивает выдачу (по умолчанию 200 строк, параметр `limit`) | Лента без предела — запрос, который растёт вместе с историей |
| Тестовая база отдельная (`TEST_DATABASE_URL` или рабочая с суффиксом `_test`) | Прогон тестов пересоздаёт схему с нуля; на рабочей базе это стёрло бы данные разработчика |
| У пула есть пределы: запрос — 10 с, ожидание свободного соединения — 3 с, соединений — 10 | Маршрут заполнения открыт в интернет, и под всплеском отказ обязан приходить быстро, а не копиться очередью. Десять секунд — это уже не «медленный запрос», а зависший: самая тяжёлая выборка продукта (лента одной станции) ограничена 200 строками и идёт по составному индексу, то есть измеряется миллисекундами; такой запрос база снимает сама и возвращает соединение в пул. Три секунды ожидания — стократный запас к штатным десяткам миллисекунд и при этом быстрый отказ вместо спиннера: сотрудник пересканирует код. Десять соединений заданы явно, а не унаследованы у драйвера: совпадение с его нынешним умолчанием — не решение, и обновление драйвера не должно менять нагрузку на базу молча. Десятки сканирований в минуту на пересменке эти десять соединений перекрывают многократно, а бюджет PostgreSQL (`max_connections` = 100, проверено на стенде) остаётся свободен для миграций, `psql` и второго экземпляра приложения во время выкладки. Миграции идут мимо этого пула (свой `Pool` в `migrator` и в подготовке тестовой базы), поэтому предел времени запроса не режет длинный DDL |

## Журнал работы

| Задача | Кем | Что сделано |
|---|---|---|
| T008 | сам | Схема семи таблиц на Drizzle 0.45.2, типы `Item`/`Section`/`Answer` через `.$type<T>()`. Схема — не механическая работа и прямое исключение из правила делегирования |
| T009 | сам | Миграции `0000_init` вперёд и назад, частичные уникальные индексы (одна опубликованная версия, один черновик), `check` на согласованность состояния и номера. Проверено: накат на пустую базу, откат, повторный накат — на выброшенной базе, создаваемой тестом. Отрицательный прогон: индекс ослаблен до неуникального — тест упал (`expected undefined to be '23505'`); обратный файл лишён одной таблицы — тест упал (`expected [ 'blocks' ] to strictly equal []`) |
| T010 | сам | `publishVersion` вставкой строки, прежняя версия уходит в архив без правки содержимого; блокировка черновика разводит одновременные публикации. Ключевое правило продукта — делегированию не подлежит. Отрицательный прогон: архивация научена заодно переписывать секции — тест «прежняя версия не меняется» упал |
| T011 | сам | `getPublishedVersionForStation` и `getDraft`: окно полуоткрытое, работает через полночь, неизвестный и пустой код дают `null`, черновик наружу не уходит. Отрицательный прогон: конец окна сделан включительным — тест границ упал (`expected { version… } to be null`) |
| T012 | исполнитель | Слой заполнений (`saveSubmission`, `listSubmissions`, `getSubmission`): механические запросы по готовому контракту, без миграций и политик доступа — ровно тот случай, когда задача обязана уходить исполнителю. 14 тестов исполнителя зелёные |
| T012 — приёмка | сам | Разбор кода исполнителя нашёл дефект: карточка и лента читали пункты из версии, а не из снимка заполнения — снимок хранился впустую. Написан падающий тест (`expected [ { id: 'section-подменённый' … } ] to strictly equal [ { id: 'section-опора' … } ]`), затем исправлено. Заодно поднят нижний предел `limit`: отрицательное значение роняло запрос ошибкой драйвера |
| T056 | сам | Гонка со станцией закрыта заморозкой: колонка `checklist_versions.station_id`, миграция `0001_version_station` с переносом уже опубликованных версий на текущую привязку и обратным файлом. `publishVersion` замораживает станцию в транзакции публикации, `saveSubmission` читает её из версии (джойн на `checklists` больше не нужен), `getPublishedVersionForStation` отдаёт версию только своей станции. Схема и миграции — прямое исключение из правила делегирования. **Отрицательный прогон:** оба теста написаны до правки и упали на ней — заполнение уехало на чужую станцию (`expected '470124cd…' to be '606b4288…'`), а перевязанный чек-лист отдал прежнюю версию на новой станции (`expected { version… } to be null`) |
| T057 | сам | `CHECK (window_start <> window_end)` на `checklists` миграцией `0002_window_not_empty`. Запрещены только равные границы: конец раньше начала — обычное окно через полночь, и вторым тестом закреплено, что оно проходит. Ограничение базы — снова исключение из делегирования. **Отрицательный прогон:** тест написан до правки и упал на ней (`expected undefined to be '23514'` — база приняла окно 08:00–08:00) |
| T058 | сам | Пределы размера JSONB в самой базе миграцией `0003_jsonb_size_limits`: `sections` версии и `snapshot` заполнения — 256 КиБ, `answers` — 64 КиБ. Числа не из головы: замерено `pg_column_size` на PostgreSQL 17 — чек-лист на 50 пунктов с двумя языками и подсказками занимает 22 КБ, ответы на него с комментариями 7 КБ, то есть запас на порядок. `pg_column_size` внутри `CHECK` видит несжатый размер (проверено: 1 МБ повторов даёт 1 000 017 байт), поэтому предел не зависит от удачи сжатия. Ограничение в базе — снова схема, делегированию не подлежит; числа к тому же надо было замерить, а не выписать. Нижнюю сторону держит отдельный тест: настоящий чек-лист на полсотни пунктов проходит. **Отрицательный прогон:** три теста написаны до правки и упали на ней (`expected undefined to be '23514'` — база принимала 400 000 символов) |
| T059 | сам | Вторичный ключ сортировки ленты `(submitted_at desc, id desc)` и составной индекс `(station_id, submitted_at desc)` миграцией `0004_feed_order`. Прежний индекс по одной `station_id` снят: он левый префикс нового, то есть лишняя запись на каждое сохранение в публичной точке записи; обратный файл его возвращает. План проверен на живой базе — фильтр «станция + период» идёт по составному индексу. Смена индексов — миграция, то есть исключение из делегирования. **Отрицательный прогон:** тест на 500 заполнений с одинаковой отметкой времени написан до правки и упал на ней (`expected [ …(200) ] to strictly equal [ …(200) ]` — порядок был не по id) |
| T060 | сам + исполнитель | Пул создавался как `new Pool({ connectionString })` — без единой настройки: ожидание свободного соединения не ограничено ничем (`connectionTimeoutMillis` по умолчанию 0), время запроса тоже (`show statement_timeout` на стенде — `0`). Заданы три предела: `statement_timeout` 10 000 мс, `connectionTimeoutMillis` 3 000 мс, `max` 10 — обоснование каждого числа строкой выше, в решениях блока. Красный тест написал исполнитель по готовому контракту: проверки сформулированы мной до его запуска, работа механическая — ровно тот случай, когда задача обязана уходить исполнителю. Выбор значений и правка `client.ts` — сам. **Отрицательный прогон:** оба теста написаны до правки и упали на ней — `expected '0' to be '10000'` (сессия без предела времени запроса) и `expected 'повис в очереди' to match /^отказал: .*timeout/i` (одиннадцатое соединение ждало вечно, сторож сработал раньше отказа). После правки оба зелёные |
| T061 | сам, коммит диспетчера | Тест на пересечение окон двух чек-листов одной станции: правило «побеждает начинающийся раньше» жило комментарием в реализации и ни разу не запускалось. Тест закрывает обе стороны — 12:00 попадает в оба окна и отдаёт раннее, 16:00 попадает только в позднее, иначе проверка не отличала бы правило от «всегда первый созданный».
