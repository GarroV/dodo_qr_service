# Готовые решения — разведка (Forge discovery)

Направление: что уже существует и закрывает часть задачи цифровых чек-листов
(редактор с секциями и библиотекой блоков, публичное заполнение по QR без
авторизации, генератор QR/печать A4, версионирование чек-листов).

Стек продукта: Next.js (App Router, TS), PostgreSQL, Drizzle ORM, Tailwind.

Пишу находки по одной, по мере поиска. Для каждой: ссылка, лицензия,
живость, что берём/почему не берём.

---

## 1. Движки форм и конструкторы чек-листов с версионированием

### SurveyJS (survey-library + survey-creator)

- **Рендерер форм**: https://github.com/surveyjs/survey-library — MIT,
  живой (последний пуш сегодня, 2026-09-05), 4867 звёзд. Прочитан README
  целиком. Рендерит формы из JSON-схемы (секции = "pages"/"panels",
  типы вопросов, валидация, условная логика). Хранение — просто JSON,
  что и куда сохранять — решает вызывающий код.
- **Визуальный конструктор (drag-and-drop builder)**:
  https://github.com/surveyjs/survey-creator — лицензия **НЕ MIT**: файл
  LICENSE (прочитан целиком,
  https://github.com/surveyjs/survey-creator/blob/master/LICENSE) —
  коммерческий EULA от Devsoft Baltic OÜ, платная лицензия на
  разработчика для бизнес-использования. Значит именно тот компонент,
  который ближе всего к нашему "редактору чек-листов", свободно
  использовать нельзя.
  - **Вывод**: рендерер (survey-library) можно было бы взять для показа
    публичного экрана заполнения, но у нас входные данные проще (да/нет,
    число, текст, критичность), а хочется полного контроля над
    построчным вводом с клавиатуры и вставкой из буфера — то, чего
    SurveyJS из коробки не даёт (это конструктор с формами-полями, а не
    построчный текстовый ввод). Тянуть тяжёлую библиотеку (survey-core
    ~ несколько сотен КБ) ради рендера да/нет/число/текст неоправданно.
    **Своё**: пишем свой рендерер на Tailwind под 3 типа ответов — это
    тривиальная задача, а конструктор всё равно не переиспользовать
    (закрытая лицензия). SurveyJS не берём.

### form.io (formio.js + formio server)

- https://github.com/formio/formio.js — **MIT**, живой (пуш
  2026-09-04), 2086 звёзд. "JavaScript powered Forms with JSON Form
  Builder" — в отличие от SurveyJS, сам билдер тут MIT.
- https://github.com/formio/formio — серверная платформа форм, лицензия
  **Open Software License 3.0** (OSL-3.0) — копилефт-лицензия с
  особенностями (модификации веб-сервиса должны публиковаться), живой
  (пуш 2026-09-02), 2314 звёзд.
  - **Просмотрено по заголовкам** (README, не всё целиком) — оценка по
    структуре репозитория (`src/`, docs на formio.com).
  - **Вывод**: formio.js (билдер, MIT) теоретически годится как основа
    JSON-схемы форм, но это полноценный движок форм общего назначения
    (сложные условия, много типов компонентов, свой рантайм) — тяжелее,
    чем нужно для 3 типов ответов + секции + библиотека блоков.
    Заводить формио как зависимость means подстраивать нашу модель
    "секция → пункт → тип ответа → критичность" под их модель
    компонентов, что сложнее, чем написать свою схему на 4 таблицы
    Drizzle. **Не берём**, но держим в уме как референс JSON-схемы форм
    с вложенными компонентами, если понадобится более сложная логика
    условных пунктов в будущем.

### ODK / KoboToolbox / Enketo (экосистема сбора данных в полях)

- https://github.com/getodk/central — сервер ODK, **Apache-2.0**, живой
  (пуш 2026-09-04), 223 звезды.
- https://github.com/getodk/collect — Android-клиент, лицензия Other
  (по факту Apache-подобная с доп. условиями), живой, 786 звёзд —
  нерелевантно (нативное Android-приложение, не веб/React).
- https://github.com/enketo/enketo-express — веб-рендерер форм ODK
  (XForms → веб), Apache-2.0, но **repo заархивирован**
  (`archived: true`, последний пуш 2023-11-29) — мёртвый проект,
  не берём.
- https://github.com/kobotoolbox/kpi — сервер KoboToolbox с
  "question library" (переиспользуемые вопросы/блоки — концептуально
  близко к нашей "библиотеке переиспользуемых блоков"), AGPL-3.0,
  живой (пуш 2026-09-04), 181 звезда. Просмотрено по заголовкам README,
  не читал код целиком.
  - **Вывод**: вся экосистема ODK/Kobo заточена под офлайн-сбор данных в
    полевых условиях (XForms, ODK XML, ODATA) — модель тяжелее и старше
    нашей задачи, стек Python/Django + Angular, не Next.js/Drizzle.
    AGPL/OSL лицензии сервера означают риск copyleft-обязательств при
    встраивании. Концепция "библиотеки переиспользуемых вопросов" у
    kpi подтверждает, что паттерн разумный, но код брать не будем —
    несовместимый стек и лицензии. **Не берём код, берём только
    паттерн** (общая библиотека блоков с редактированием в одном месте
    — см. раздел 5 про схему хранения).

### Formbricks

- https://github.com/formbricks/formbricks — "Open Source Qualtrics
  Alternative", лицензия **Other** (не MIT — нужно проверить точный
  текст, ядро под AGPL-подобной с коммерческим переходом), живой (пуш
  2026-09-05, сегодня), 12893 звезды, Next.js + Prisma в стеке.
  Просмотрено по заголовкам (org page + README), не читал схему БД
  целиком.
  - **Вывод**: Formbricks — это продукт опросов/фидбека (NPS, in-app
    surveys), а не чек-листов, ориентирован на конечного пользователя
    сайта, а не на сотрудника с QR-станцией. Стек Next.js близкий, но
    доменная модель (опросы, таргетинг, сегменты) не совпадает с нашей
    (станции, критичные пункты, версии). Лицензия "Other" требует
    отдельной проверки, если решим смотреть глубже. **Не берём** —
    несовпадение домена перевешивает совпадение стека.

## 2. Блочные редакторы для React (построчный ввод, вставка списка)

### Editor.js + плагины

- Ядро: https://github.com/codex-team/editor.js — **Apache-2.0**, очень
  живой (пуш 2026-08-31), 31928 звёзд. Прочитан README целиком (раздел
  About/Installation). Блочный редактор: JSON-вывод, каждый блок —
  отдельный плагин-Tool, **Enter внутри блока нативно создаёт новый
  блок** — это именно та клавиатурная механика, которая нужна для
  построчного ввода пунктов.
- Плагин чек-листа: https://github.com/editor-js/checklist — MIT, но
  **последний пуш 2024-11-13** (почти два года без изменений на
  сегодня, 2026-09-05) — практически заброшен.
- Плагин списка: https://github.com/editor-js/list — MIT, последний пуш
  2025-11-15 — тоже вялый, но живее.
  - **Вывод**: Editor.js даёт нужную клавиатурную механику "из коробки",
    но это полноценный блочный редактор общего назначения (тулбар на
    каждый блок, drag-хендлы, санитайзер HTML, своя модель Tool/Block) —
    ради 3 типов ответов (да/нет, число, текст) и заголовков секций
    тянуть его излишне тяжело, а официального React-биндинга нет
    (нужны сторонние обёртки вокруг vanilla-JS инстанса, что добавляет
    хрупкости в Next.js App Router с SSR). Плагины экосистемы (checklist,
    list) единственные, что нам подошли бы, уже полузаброшены.
    **Не берём.**

### Plate.js / Tiptap (rich-text фреймворки)

- https://github.com/udecode/plate — MIT-ядро (проверено файлом LICENSE
  в корне репозитория, отдельные пакеты могут иметь другую лицензию —
  платная "Plus"-надстройка), живой (пуш 2026-09-04), 16553 звезды.
  Построен поверх Slate.js, ориентирован на rich-text с AI-функциями.
- https://github.com/ueberdosis/tiptap — **MIT**, очень живой (пуш
  2026-09-04), 38279 звёзд, headless rich-text на ProseMirror.
  - **Вывод**: оба — headless rich-text фреймворки (форматирование
    текста, markdown, комментарии, AI) — избыточны для списка пунктов
    с да/нет/числом/текстом. Наш ввод — не rich-text, а структурированные
    строки с типом ответа, это ближе к форме/таблице, чем к документу.
    **Не берём.**

### dnd-kit (для перетаскивания блоков/секций/пунктов)

- https://github.com/clauderic/dnd-kit — **MIT**, очень живой (пуш
  2026-09-05, сегодня), 17603 звёзды. "Modern toolkit for building drag
  and drop interfaces" — легковесный, без диктата структуры данных
  (в отличие от блочных редакторов).
- Альтернатива https://github.com/atlassian/react-beautiful-dnd —
  **заархивирован** (пуш 2025-08-18, `archived: true`) — не брать,
  Atlassian официально прекратил поддержку.
  - **Вывод**: **берём dnd-kit** для перетаскивания пунктов/секций/блоков
    библиотеки внутри редактора чек-листа (сортировка после
    построчного ввода) — это ровно точечная задача, для которой dnd-kit
    и создан, без нагрузки целого блочного редактора.

### Вставка многострочного текста из буфера обмена → пункты

- Целевого пакета-библиотеки под эту конкретную задачу не нашлось —
  поиском кода (`gh search code`) по паттерну
  `e.clipboardData.getData("text/plain")` + `split("\n")` нашлись только
  **самописные** реализации в разных проектах (например
  `mattnotmatthew/budget-tracker:src/hooks/useExcelPaste.ts`,
  `boostcampwm-2024/web33-Nocta:client/src/features/editor/hooks/useCopyAndPaste.ts`,
  `prostgles/ui:client/src/components/Chat/useChatOnPaste.ts`) — обычно
  10–20 строк: `onPaste` → `e.clipboardData.getData('text/plain')` →
  `split('\n')` → создать N пунктов.
  - **Вывод**: это подтверждает, что паста-в-список — не задача под
    библиотеку, а тривиальный `onPaste`-хендлер. **Пишем своё** (~20
    строк), опираясь на увиденный в этих проектах паттерн, без
    добавления зависимости.

## 3. Генерация QR-кодов и печатных листов A4

### Генерация самого QR-кода

- https://github.com/soldair/node-qrcode — **MIT**, 8170 звёзд, но
  **последний пуш 2024-08-23** (больше двух лет без изменений на
  2026-09-06) — стабильный, но не развивается. Даёт генерацию в
  SVG/PNG/data URL/terminal, есть Node API для серверной генерации.
  Просмотрено по описанию и структуре пакета в npm, не читал код целиком.
- https://github.com/zpao/qrcode.react — React-компонент `<QRCode/>`,
  лицензия ISC (прочитан LICENSE целиком — MIT-подобная разрешительная
  лицензия, никаких ограничений), живой (пуш 2026-09-01), 4283 звезды.
  - **Вывод**: **берём `qrcode` (node-qrcode)** для серверной генерации
    (Node.js API, SVG-вывод для чёткой печати) и **`qrcode.react`** —
    если понадобится рендер QR прямо в браузере (экран планшета на
    станции). Обе тривиально стабильны, конкурировать с ними смысла
    нет — генерация QR по спецификации не то место, где стоит писать
    свой код.

### Компоновка печатного листа A4 (сетка наклеек) и вывод в PDF

- Целевого пакета "лист наклеек A4" (по типу генераторов Avery-шаблонов)
  **не нашлось** — поиск `gh search repos` по фразам
  ("avery label pdf generator", "qr code sheet print labels") дал 0
  результатов, поиск кода по "A4"+"grid"+"label" тоже не дал релевантных
  попаданий. Это ожидаемо: сетка наклеек — это просто CSS Grid/Flexbox
  на печатной странице, отдельной ниши-библиотеки под неё нет.
- Для вывода в PDF на сервере рассмотрены три пути:
  - https://github.com/diegomura/react-pdf (`@react-pdf/renderer`) —
    **MIT**, очень живой (пуш 2026-09-03), 16770 звёзд. Позволяет
    описать компоновку декларативно на React-компонентах (`<View>`,
    `<Page>` с flexbox) — сетку наклеек 3×8 на A4 можно собрать тем же
    подходом, что и остальной UI. Найден живой пример использования
    именно с QR-кодами:
    `DPSolutionsLLC/WLT:lib/pdf/qrCode.ts` — генерирует QR через пакет
    `qrcode`, затем вставляет как `<Image>` в `@react-pdf/renderer`
    (просмотрено по коду фрагмента из `gh search code`, не весь файл).
  - https://github.com/akii09/pdfx — компонент-библиотека НАД
    `@react-pdf/renderer` с готовым `<PdfQRCode>`-компонентом,
    лицензия **MIT** (прочитан файл LICENSE в репозитории целиком —
    GitHub ошибочно детектит её как "Other", но текст файла — чистый
    MIT), 1174 звезды, живой (пуш 2026-08-17). Даёт готовый компонент
    вместо ручной склейки `qrcode` + `<Image>`.
  - https://github.com/puppeteer/puppeteer — **Apache-2.0**, 95550
    звёзд, очень живой (пуш сегодня) — альтернативный путь: сверстать
    лист A4 обычным HTML/CSS (Tailwind, тот же стек, что и остальной
    UI) и напечатать в PDF headless-хромом (`page.pdf()`). Тяжелее по
    рантайму (нужен браузерный процесс), но верстать печатную сетку
    в HTML/CSS проще, чем в примитивах `@react-pdf/renderer`.
  - https://github.com/foliojs/pdfkit — **MIT**, 10704 звезды, живой
    (пуш сегодня) — низкоуровневый PDF-generator (canvas-like API),
    более ручной, чем `@react-pdf/renderer`.
  - **Вывод**: **берём `@react-pdf/renderer`** как основной путь —
    декларативная компоновка на React ближе всего к остальному
    Next.js-коду, не требует браузерного процесса (легче в serverless/
    контейнере), и уже есть живой референс интеграции с `qrcode`
    (`DPSolutionsLLC/WLT`). Компонент `pdfx`'а можно взять точечно как
    пример реализации `<PdfQRCode>` (MIT позволяет), но не как
    обязательную зависимость — компонент простой, можно и переписать
    в 20 строк под свои размеры наклейки. Puppeteer держим как запасной
    план, если раскладка на `@react-pdf/renderer`-примитивах окажется
    неудобной для сложной сетки — но добавлять headless-браузер в
    рантайм ради генерации листа A4 — это утяжеление, которого стоит
    избежать, если хватит react-pdf.

## 4. Шаблоны и стартовые наборы Next.js App Router + Drizzle + PostgreSQL

Искал именно чистый минимальный старт "Next.js App Router + Drizzle +
Postgres + миграции + тесты". Прямого попадания (популярный репозиторий
ровно с таким узким набором, без лишнего) **не нашлось** — все найденные
варианты либо генераторы стека, либо готовые шаблоны с довеском
(auth-провайдеры, платежи, i18n), который придётся выпиливать.

- **`create-t3-app`** — https://github.com/t3-oss/create-t3-app — MIT,
  29108 звёзд, но **последний пуш 2025-12-13** (около 9 месяцев назад
  на сегодня, 2026-09-06) — не мёртв, но не активно развивается. Прочитан
  README: **Drizzle официально поддерживается как опция ORM** наравне с
  Prisma (строка `- [Drizzle](https://orm.drizzle.team)` в списке технологий),
  плюс Tailwind, TypeScript, NextAuth (последнее не нужно — у нас один
  пароль на админку). CLI-генератор, а не форк-репозиторий — создаёт
  Pages/App Router проект с нуля по выбранным опциям.
- **`create-better-t-stack`** — https://github.com/AmanVarshney01/create-better-t-stack
  — MIT, 5697 звёзд, очень живой (пуш 2026-09-02). Прочитан README
  целиком. Философия прямо совпадает с нашей потребностью: "Roll your
  own stack: you pick only the parts you need, nothing extra." Опции
  включают Frontend: Next.js, Backend: "Self (fullstack web app)"
  (то есть Next.js API routes/Server Actions без отдельного бэкенда),
  ORM: Drizzle, БД: PostgreSQL, DB Setup: Neon/Supabase/Docker. **Тестов
  как отдельного аддона в списке функций нет** (Addons: Turborepo, Nx,
  PWA, Biome, Lefthook, Husky и др. — Vitest/Playwright не упомянуты) —
  значит тестовый каркас всё равно придётся добавлять руками.
- **`reliverse/relivator`** — https://github.com/reliverse/relivator —
  MIT, 1558 звёзд, живой (пуш 2026-09-05). Прочитан README целиком.
  Стек в точку (Next.js 15 + Drizzle + Postgres/Neon + Tailwind +
  shadcn/ui), но это **готовый e-commerce шаблон** с better-auth,
  UploadThing, Polar-платежами, i18n — существенно больше, чем нужно
  (у нас нет ролей, нет платежей, нет каталога товаров), и работает
  через `bun db:push` (синхронизация схемы), а не через версионированные
  файлы миграций — не совпадает с требованием "миграции". **Не берём**
  как основу, слишком много выпиливать.
- Официального актуального примера от Vercel (`vercel/next.js/examples`)
  или от самой команды Drizzle (`drizzle-team/drizzle-examples`) —
  **не нашлось**: папки `examples` в `vercel/next.js` под drizzle нет
  (проверено `gh api` по каталогу), а репозиторий
  `drizzle-team/drizzle-examples` — **пустой** (0 звёзд, `pushed_at`
  2024-04-12, содержимого нет).
  - **Вывод**: **своё**, начиная с `create-better-t-stack`
    как генератора первого коммита (Next.js + Drizzle + Postgres +
    Tailwind, backend "Self", без Better Auth/Clerk — методист входит
    по одному паролю, это не полноценная auth-система) — берём только
    сгенерированный каркас (package.json, конфиги drizzle-kit, структура
    app router), выкидываем то, что не выбрано на шаге CLI. Тесты
    (Vitest для unit, Playwright/Testing Library для e2e) добавляем
    сами — готового аддона под это ни у одного варианта нет. Файлы
    миграций через `drizzle-kit generate` + `drizzle-kit migrate` (а не
    `db:push`) — стандартный путь самого Drizzle, не специфика шаблона.

## 5. Схемы версионируемых форм в PostgreSQL/JSONB — реальные примеры кода

Искал через `gh search code` по паттернам `pgTable`+`jsonb`+`version` и
`checklist`+`version`+`jsonb`. Нашлись четыре живых репозитория с разным,
но пересекающимся решением ровно нашей задачи (версия чек-листа не
мутирует, заполнение ссылается на зафиксированный снимок). Все файлы
ниже прочитаны как минимум в релевантном фрагменте (указано, что именно).

### Вариант А: одна таблица "шаблон", версия — целочисленная колонка, партиционный уникальный индекс на "активную" версию

`Stephen-C-Noh/mat-inspect` — https://github.com/Stephen-C-Noh/mat-inspect/blob/main/db/schema/checklist-templates.ts
(лицензия репозитория — Other/нестандартная, GitHub не распознал явно;
2 звезды, пуш 2026-08-20 — маленький личный проект, но схема читается
как продуманная). Прочитан файл целиком. Ключевая конструкция (Drizzle):

```ts
export const checklistTemplates = pgTable('checklist_templates', {
  id: uuid('id').primaryKey().defaultRandom(),
  equipmentType: equipmentTypeEnum('equipment_type').notNull(),
  version: integer('version').notNull(),
  isActive: boolean('is_active').notNull().default(false),
  effectiveFrom: timestamp('effective_from', { withTimezone: true }).notNull().defaultNow(),
  items: jsonb('items').$type<ChecklistItemRecord[]>().notNull(), // весь чек-лист одним jsonb-массивом
  createdBy: uuid('created_by').notNull().references(() => users.id),
  reviewedBy: uuid('reviewed_by').references(() => users.id),
  createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
}, (table) => [
  uniqueIndex('checklist_templates_one_active_per_type')
    .on(table.equipmentType).where(sql`${table.isActive} = true`), // партиционный уникальный индекс — только одна активная версия на тип
  uniqueIndex('checklist_templates_type_version').on(table.equipmentType, table.version),
]);
```

Комментарий в коде поясняет корректность: "переактивация старой версии
безопасна — в одной транзакции сначала снимается активность с текущей
строки, потом ставится на целевую, поэтому индекс никогда не видит две
активные строки одновременно". Каждая публикация — новая строка, старые
не трогаются (то, что нам и нужно для "правка не меняет исторические
заполнения").

### Вариант Б: родитель + версии отдельной таблицей, состояние черновик/финал

`chrisxvin/checklist` — https://github.com/chrisxvin/checklist/blob/main/src/lib/server/db/proc.checklist.ts
(MIT, пуш 2026-08-16, 0 звёзд — маленький personal-проект, но логика
показательная). Прочитан файл целиком (SQL-процедуры на postgres.js,
не Drizzle, но схема таблиц ясна из запросов): таблица `checklist`
(родитель: `slug`, `current_version`, `drafting: boolean`) + таблица
`checklist_version` (`list_id`, `version`, `steps jsonb`). Механика:

- Если чек-лист уже финализирован (`drafting = false`) и его открывают
  на редактирование — **создаётся новая строка** в `checklist_version`
  копированием `steps` предыдущей версии, и `checklist.current_version`
  переключается на неё:
  ```sql
  INSERT INTO checklist_version (list_id, version, steps)
  VALUES (${listId}, ${newVer}, (SELECT steps FROM checklist_version WHERE list_id = ${listId} AND version = ${row.version}))
  ```
- Пока черновик (`drafting = true`) — редактирование делает `UPDATE`
  той же строки версии (`steps = ...`), без размножения версий на
  каждое нажатие клавиши.
- `finalize(listId)` переключает `drafting` в false — версия
  "замораживается", последующая правка снова создаст новую версию.

Это отвечает прямо на требование "публикация неизменяемых версий":
пока не опубликовано — мутируем текущий черновик; опубликовали —
следующая правка форкает новую версию, старая остаётся как есть для
уже сделанных заполнений.

### Вариант В: живая таблица + отдельная append-only таблица снимков

`talkpush-apacse/UAT` — https://github.com/talkpush-apacse/UAT/blob/main/src/lib/actions/checklist.ts
(лицензия не указана в репозитории — код можно смотреть как референс,
но не копировать дословно; пуш 2026-08-22, 0 звёзд). Прочитан
релевантный фрагмент файла (функция `importChecklist`). Паттерн другой:
основная таблица `checklist_items` **мутируется** напрямую (это не
версионируемый источник правды), а перед каждой разрушающей операцией
берётся автоматический снимок в `checklist_snapshots`:

```ts
await supabase.from('checklist_snapshots').insert({
  project_id: projectId,
  version_number: nextVersion,
  label: 'Auto-save before import',
  item_count: existingItems.length,
  snapshot_data: existingItems, // весь массив пунктов как jsonb
})
```

- **Отличие от вариантов А/Б**: здесь "источник правды" — мутируемая
  таблица, а версии существуют только как резервные копии для отката,
  не как основа для ссылки из заполнений. **Это не подходит** для
  нашего требования (заполнение обязано ссылаться на неизменную
  версию, а не полагаться на то, что снимок кто-то не удалит) — но
  паттерн `snapshot_data jsonb` как способ хранить "весь чек-лист на
  момент X" одной колонкой валиден и для нас (см. ниже, для таблицы
  заполнений).

### Вариант Г: библиотека переиспользуемых блоков через FK на отдельную таблицу

`chaibuilder/core` — https://github.com/chaibuilder/core/blob/main/src/actions/drizzle/schema.ts
(BSD-3-Clause, живой — пуш 2026-08-03, 474 звезды, open-source
конструктор сайтов). Прочитан релевантный фрагмент файла (таблицы
`library_items`, `apps_pages_online`). Ключевая конструкция:

```ts
export const libraryItems = pgTable("library_items", {
  id: uuid().defaultRandom().primaryKey().notNull(),
  library: uuid(), // FK → libraries.id — группировка библиотек
  name: text(),
  blocks: jsonb().default([]), // содержимое переиспользуемого блока
  group: text().default('general'),
}, (table) => [
  foreignKey({ columns: [table.library], foreignColumns: [libraries.id], name: "library_items_library_fkey" }),
]);
```

а страница (`app_pages_online`) хранит **свой** `blocks: jsonb` плюс
`libRefId: uuid()` — указатель на исходный элемент библиотеки. Это
прямое подтверждение паттерна "блок заводится один раз в отдельной
таблице с jsonb-содержимым, вставляется в десятки страниц по ссылке
(FK), правка блока — в одном месте (`library_items`), а конкретная
страница держит собственную копию/ссылку для рендера" — ровно то, что
нужно для нашей "библиотеки переиспользуемых блоков чек-листа".

### Вывод — рекомендуемая схема для нашего продукта

Ни один пример не переиспользуем как зависимость (это код чужих
приложений, не библиотека), но **комбинация паттернов А+Г покрывает
всю задачу**, и её можно взять как референс архитектуры:

1. **`checklist_blocks`** (библиотека, паттерн Г из chaibuilder):
   `id`, `title`, `items: jsonb` (пункты блока) — редактируется в одном
   месте, ссылки из секций чек-листов идут по `block_id` (FK).
2. **`checklists`** (семья/родитель) + **`checklist_versions`**
   (паттерн А из mat-inspect + Б из chrisxvin/checklist): `checklist_id`,
   `version: integer`, `is_published: boolean` с партиционным уникальным
   индексом "одна опубликованная версия активна", `sections: jsonb`
   (каждая секция — заголовок + список пунктов, пункты — либо инлайн,
   либо `{ blockRef: block_id }` с зафиксированным на момент публикации
   содержимым блока — снимок, а не живая ссылка, иначе правка библиотеки
   задним числом изменит уже опубликованные версии, что запрещено
   требованием). Публикация = INSERT новой строки версии, а не UPDATE.
3. **`checklist_fills`** (заполнения, паттерн В из talkpush/UAT для
   формы хранения): `checklist_version_id` (FK на зафиксированную
   версию — не на "текущую" `checklists`), `answers: jsonb` (ответы по
   пунктам) + `snapshot: jsonb` при желании держать полный текст
   чек-листа денормализованно для быстрого показа истории без JOIN'а
   через версию.

Это стандартная связка "event-sourcing-lite" для форм (форк-на-публикацию
+ FK на зафиксированную версию из заполнения) — не нужно тянуть
библиотеку, четырёх таблиц Drizzle с партиционным уникальным индексом
достаточно, что подтверждается всеми четырьмя найденными живыми
примерами.
