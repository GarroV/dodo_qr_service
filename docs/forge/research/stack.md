## 1. Next.js

**Источник:** официальный блог nextjs.org (прочитан полностью: https://nextjs.org/blog/next-16), GitHub Releases (просмотрены заголовки: https://github.com/vercel/next.js/releases), npm registry (частично — упёрся в лимит размера ответа инструмента, но версия подтверждена через WebSearch и GitHub releases).

### Актуальная версия
- Мажорная линия — **Next.js 16** (анонс 21 октября 2025: https://nextjs.org/blog/next-16). Последний стабильный патч на начало сентября 2026 — **16.3.4** (конец августа 2026), подтверждено списком релизов на GitHub (https://github.com/vercel/next.js/releases).
- Активная разработка идёт в ветке 16.4.0-canary (много канареечных сборок конца августа/начала сентября 2026) — это НЕ стабильная версия, для продакшена не берём.
- Была security-раскатка: **16.3.3** — релиз с исправлением двух critical-severity уязвимостей (упомянуто в списке релизов GitHub, конкретные CVE не проверял детально — стоит свериться с https://github.com/vercel/next.js/security/advisories перед стартом проекта). 16.3.4 — бэкпорт багфиксов поверх неё.
- Next.js 15 всё ещё сопровождается патчами (15.5.25 вышла тем же днём, что и 16.3.4) — это ветка предыдущего мажора для тех, кто не мигрировал; новый проект её не касается.

### App Router и Server Actions
- App Router — основной и единственный рекомендуемый способ строить приложение в 16-й линии (Pages Router по-прежнему поддерживается для обратной совместимости, но весь новый функционал идёт в App Router).
- Server Actions работают поверх React 19.2 (App Router в Next 16 использует канареечный React с уже стабилизированными фичами 19.2: View Transitions, `useEffectEvent`, `<Activity/>`) — https://nextjs.org/blog/next-16#react-192-and-canary-features.
- Кеширование серьёзно переработано: новая модель **Cache Components** (`"use cache"` директива + `cacheComponents: true` в `next.config.ts`) заменяет прежний экспериментальный `experimental.ppr`/`dynamicIO`. Это ключевое изменение против Next 15 — если конфигурировать кеш по старым докам/статьям, попадёте на удалённые флаги.
- `revalidateTag()` теперь **требует** второй аргумент — профиль `cacheLife` (например, `revalidateTag('tag', 'max')`); однопараметрический вызов помечен deprecated. Добавлен новый `updateTag()` для семантики read-your-writes в Server Actions и `refresh()` для обновления некешированных данных.
- `middleware.ts` переименован в `proxy.ts` (функция `proxy` вместо `middleware`) — `middleware.ts` ещё работает для Edge-рантайма, но deprecated и будет удалён в будущей версии.

### Важные подводные камни (breaking changes против Next 15)
- **Node.js 20.9+ обязателен**, Node 18 больше не поддерживается — https://nextjs.org/blog/next-16#breaking-changes-and-other-updates.
- **TypeScript 5.1.0+ обязателен**.
- `params` и `searchParams` — **только асинхронные** (`await params`), синхронный доступ убран полностью (раньше было предупреждение, теперь ошибка). Аналогично `cookies()`, `headers()`, `draftMode()` — только `await`.
- `next lint` команда **удалена** — линт теперь на ESLint/Biome напрямую, `next build` линт не гоняет. Есть кодмод: `npx @next/codemod@canary next-lint-to-eslint-cli .`
- Turbopack — **дефолтный бандлер** и для dev, и для prod-сборки (webpack остаётся опцией через `--webpack`). Для нового проекта это дефолт "из коробки", ничего специально включать не нужно.
- `next/image`: у локальных src с query-строками теперь требуется `images.localPatterns` (защита от enumeration-атак) — актуально для генератора QR/PDF, если картинки будут отдаваться через query-параметры.
- Parallel routes: слоты теперь **обязаны** иметь явный `default.js`, иначе сборка падает — не относится к MVP без параллельных роутов, но держать в уме.
- `images.qualities` по умолчанию сузился до `[75]` (раньше `[1..100]`) — если для QR/печати нужно другое качество картинок, придётся явно расширять конфиг.

### Рекомендация
Брать **Next.js 16 (16.3.4 на дату старта, дальше — актуальный патч 16.3.x)**, App Router, Node.js — см. раздел про Node ниже. Заложить в техплан: асинхронные `params`/`cookies()`/`headers()` (обязательны, не опция), `proxy.ts` вместо `middleware.ts`, ESLint напрямую вместо `next lint`, при настройке кеша ориентироваться на актуальную доку Cache Components, а не на статьи про `experimental.ppr`/`dynamicIO` — они относятся к более старым версиям и приведут к неработающему конфигу.

### Node.js — какую версию закладывать
**Источник:** официальный график релизов Node.js, сырые данные из https://raw.githubusercontent.com/nodejs/Release/main/schedule.json (прочитан как структурированные данные, не пересказ).

На сентябрь 2026 фактическое состояние линий:
- **Node 20 "Iron"** — end-of-life **30 апреля 2026**, то есть на дату исследования уже снят с поддержки апстримом, несмотря на то что Next.js 16 формально требует "20.9+". Использовать для нового проекта нельзя — не будет security-патчей.
- **Node 22 "Jod"** — Active LTS с 29 октября 2024, **перешёл в Maintenance LTS 21 октября 2025**; то есть на сентябрь 2026 это уже поддерживаемая, но угасающая ветка (maintenance-режим — только критические фиксы). EOL — 30 апреля 2027.
- **Node 24 "Krypton"** — **Active LTS с 28 октября 2025**, maintenance начнётся 20 октября 2026, EOL — 30 апреля 2028. Это актуальная рекомендуемая ветка на дату исследования.
- **Node 26** — стартовал 5 мая 2026, станет Active LTS 28 октября 2026 (то есть на сентябрь 2026 это ещё "Current", не LTS) — рано брать для продакшена без необходимости.

**Рекомендация:** брать **Node.js 24 (Krypton, Active LTS)** — минимум, который требует Next.js 16 (20.9+), формально ниже, но Node 20 уже без апстрим-поддержки на дату старта проекта, поэтому фактический выбор — 24.x, а не минимально допустимая версия.

## 2. Drizzle ORM

**Источник:** официальная документация orm.drizzle.team (страницы column-types/pg и kit-overview — прочитаны целиком через рендер, не по памяти), **npm registry напрямую через `curl` (сырой JSON, самый надёжный источник в этом разделе — без посредника-суммаризатора)**: `https://registry.npmjs.org/drizzle-orm` и `/drizzle-kit`, GitHub API `https://api.github.com/repos/drizzle-team/drizzle-orm/releases`.

### Актуальная версия — важный нюанс со статусом релиза
Пакет **уже больше года находится в переходе на v1.0**, но на дату исследования (5-6 сентября 2026) `latest`-тег на npm ещё **не переключён на 1.0**:

- `drizzle-orm`: npm dist-tag `latest` = **0.45.2** (опубликован 2026-03-27). Тег `rc` = **1.0.0-rc.4** (2026-06-27). Есть даже более свежая пре-релизная сборка под тегом `rc5` = `1.0.0-rc.5-169397b` (2026-08-12), тоже не promoted в `latest`.
- `drizzle-kit`: та же картина — `latest` = **0.31.10** (2026-03-17), `rc` = **1.0.0-rc.4** (2026-06-27), `rc5` = `1.0.0-rc.5-ab785fc` (2026-08-11).
- На GitHub у `drizzle-team/drizzle-orm` последний релиз в списке — **v1.0.0-rc.4** (2026-06-27T16:10:26Z, помечен `prerelease: true`) — то есть даже основной репозиторий ещё не выпустил финальный тег 1.0.0, только RC.
- Проверено сырым запросом к registry, а не пересказом статьи — этот факт легко потерять, если ориентироваться на блог-посты "Drizzle 1.0 уже здесь" (которые в вебе встречаются и создают ложное впечатление, что стабильный 1.0 уже доступен по умолчанию через `npm install`).

**Что это значит для проекта:** `npm install drizzle-orm drizzle-kit` без указания версии на сентябрь 2026 поставит **0.45.2 / 0.31.10** — это и есть текущий предсказуемый стабильный вариант. Ставить `@rc` вручную ради v1.0 в MVP чек-лист-сервиса без офлайн-режима смысла нет — RC не обязан быть feature-complete и может ловить регрессии перед финальным релизом.

### drizzle-kit и миграции
Команды (документация `kit-overview`, прочитана целиком): `generate` (генерация SQL-миграций из схемы), `migrate` (применение), `push` (прямой пуш схемы без файлов миграций — для прототипирования), `pull` (интроспекция существующей БД), `studio` (GUI), `check` (проверка миграций на коллизии), `up` (апгрейд снапшотов), `export` (схема → чистый DDL). Конфиг — `drizzle.config.ts` с минимум диалектом и путём к схеме.
Для проекта с публикацией неизменяемых версий чек-листов рекомендуемый паттерн — `generate` + `migrate` (миграции файлами, версионируются в git), а не `push` (тот полезен только для локального прототипирования, не для управляемых миграций в проде).

### JSONB и типизация JSON-полей
Прочитано по документации `column-types/pg`: `json()` и `jsonb()` — раздельные типы (jsonb хранится в бинарном декомпозированном виде, json — как текст по RFC 7159; для чек-листов с секциями/блоками обычно берут `jsonb` — быстрее операции сравнения и индексация через GIN).
Типизация: `.column.$type<T>()` — компилируемая TS-типизация формы JSON прямо в определении схемы:
```ts
json: jsonb().$type<{ foo: string }>();
```
**Важная оговорка из самой документации:** это **не проверяет данные в рантайме** — только компайл-тайм подсказка типов. Для входных данных с публичного экрана (заполнение по QR без авторизации) это значит, что валидацию структуры ответа (какие типы блоков, какая форма JSON) всё равно надо делать явно рантайм-схемой (zod и т.п.) на границе API, а не полагаться на `.$type<T>()`.

### Сравнение с Prisma — по трём пунктам

**Источники:** официальный блог Prisma (прочитаны частично, через fetch-суммаризацию: `prisma.io/blog/rust-free-prisma-orm-is-ready-for-production`), официальная документация `prisma.io/docs/orm/prisma-client/special-fields-and-types/working-with-json-fields` (прочитана целиком), **npm registry напрямую** для версии Prisma.

1. **JSONB / типизация JSON.** У Prisma JSON-поле в сгенерированном клиенте типизируется как `Prisma.JsonValue` (`string | number | boolean | null | JsonObject | JsonArray`) — **это встроенное поведение, и оно принципиально не типизирует форму** содержимого. Собственная документация Prisma прямо указывает, что для строгой типизации нужен **сторонний генератор** `prisma-json-types-generator` — не входит в ядро. У Drizzle типизация формы JSON — часть публичного API (`.$type<T>()`), без сторонних пакетов, хотя тоже только compile-time. **Для этого проекта (структура секций/блоков чек-листа как JSONB) Drizzle даёт нужное из коробки, Prisma — только через community-надстройку.**

2. **Миграции.** Prisma Migrate генерирует SQL-миграции похожим образом (`prisma migrate dev` / `deploy`), это зрелый и обкатанный механизм. Drizzle Kit решает ту же задачу (`generate`/`migrate`), но менее многолетний. Для MVP без сложных сценариев (без множественных схем, без сложного data-migration тулинга) паритет практический — оба варианта рабочие; Prisma Migrate чуть более документирован по продвинутым сценариям (shadow database, drift detection), Drizzle Kit проще концептуально (SQL-first, миграции читаемы как обычный SQL-файл, без бинарного shadow-DB процесса).

3. **Холодный старт.** До недавнего времени это было сильным доводом в пользу Drizzle: Prisma Client исторически тянул **Rust-бинарник query-engine** (~14 МБ, ~7 МБ gzip), что заметно било по холодному старту в serverless/edge. Это уже **не актуально** — Prisma **v6.16.0 (10 сентября 2025)** сделала Rust-free движок (TypeScript/WASM ядро) generally available: размер упал до ~1.6 МБ (~600 КБ gzip), холодный старт и память заметно улучшились (см. блог Prisma "Rust-free Prisma ORM is Ready for Production"). Drizzle же изначально не имеет отдельного бинарного движка — это тонкий TS-слой поверх драйвера БД, поэтому по чистому холодному старту паритет практически восстановился, но у Drizzle меньше движущихся частей (нет отдельного generation-step перед стартом рантайма, тогда как Prisma всё ещё требует `prisma generate` для клиента).

**Версия Prisma на сентябрь 2026 (проверено сырым запросом к npm registry):** dist-tag `latest` у пакета `prisma` внезапно указывает на **8.0.0-rc.13** (опубликован 2026-09-04, за день до даты исследования!) — это RC, не финальный релиз. Последняя стабильная (non-prerelease) версия — **7.10.0** (2026-08-25), тег `prev`. То есть у Prisma сейчас похожая на Drizzle ситуация: свежий мажор в RC, `latest`-тег временно указывает на пререлиз — при установке `prisma@latest` без фиксации версии можно случайно получить нестабильный 8.0 RC. Внимание: это нетипичное поведение dist-tag `latest` (обычно он должен указывать только на стабильные версии) — стоит перепроверить перед стартом проекта, не изменилось ли к моменту реальной установки.

### Рекомендация
Брать **Drizzle ORM 0.45.2 + drizzle-kit 0.31.10** (актуальный стабильный дуэт на дату исследования, НЕ переходить на `@rc` ради v1.0 — он ещё не promoted в `latest` даже у самих мейнтейнеров). Для JSONB-полей секций/блоков чек-листа использовать `jsonb().$type<T>()` и дублировать структурную валидацию через zod на границе API (Server Action / route handler), не полагаясь на compile-time типизацию колонки. Prisma в этом проекте не берём: встроенная типизация JSON слабее (нужен сторонний генератор), миграции через генерируемый SQL проще стыкуются с git-версионированием неизменяемых публикаций чек-листов, а исторический аргумент "Prisma тяжелее на холодном старте" уже неактуален после Rust-free GA — но и не даёт Prisma решающего преимущества, чтобы менять выбор владельца.
